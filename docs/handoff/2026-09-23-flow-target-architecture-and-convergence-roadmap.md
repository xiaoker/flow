## 2. 终局产品合同：用户到底得到什么

### 2.1 产品定位

Flow 是低成本、日频、官方事实驱动的市场观察工具，不是实时交易系统、逐笔资金追踪系统，也不是机构持仓猜测系统。

产品交付三层信息，标题、图例、排序、单位和下载数据必须一致：

| 层级 | 内容 | 禁止越界 |
| --- | --- | --- |
| 官方事实 | ETF 份额、NAV、成交额、融资融券披露、原始业务日期 | 未披露不能标成零；发布时间不能代替业务日期 |
| 公式计算 | 份额差、板块汇总、已定义的余额变化 | 余额不等于当日净买入，ETF 总份额不是特定持有人的持仓 |
| 模型估算 | PCF 篮子等价数量、金额估算 | 不是个股实际成交或真实现金流；两个板块的增减不能证明同一笔钱迁移 |

“国家队”统一表达为 ETF 观察池，除非持有人披露确实支持相应结论。板块轮动使用“净增/净减分布”等描述；不能用因果连线或文案暗示已追踪到资金从 A 转到 B。解释不只放在页脚。

### 2.2 新鲜度、完整性与可用性分开

- **新鲜度**：这份数据属于哪一个业务日，是否晚于预期。
- **完整性**：该能力、样本集合和周期是否满足自己的覆盖合同。
- **可用性**：用户能否读取已验证版本；新数据失败不应让旧有效版本消失。

最新核心 ETF 日已完成，不代表互联互通、两融、穿透和十二月窗口都完成。页面不得继续用一个“完整数据截至”标签掩盖这种差别。

### 2.3 能力分级的确定建议

以下是本路线图的目标合同，须经 v0.7 合同与候选验证后才能改变现有生产门禁：

1. `etf_daily_core`：同日 SSE+SZSE ETF 事实、真实相邻基准、统一分类和核心日频对账。它是本产品全局“最新 ETF 日”的推进条件。
2. `dashboard`：呈现外壳，不再把所有数据域定义成一个不可拆的来源依赖。
3. `etf_radar`、`rotation`、观察池：依赖同一核心 ETF 日事实；缺某个长周期只影响对应列/图。
4. `connect`、`margin`：各自完整才可用，不得拿另一日期暗中补齐；未就绪时不阻断已可信的核心 ETF 日。
5. `etf_penetration`、`stock_search`、`stock_detail`：依赖同日且来源可证明的 PCF/模型能力；必须一致发布。
6. `etf_periods`：按“指标 × 周期 × 样本范围”逐项判定，不再只有一个全局布尔值。

同一日期 D 的页面只引用 D 的已验证能力；未就绪能力明确留空。用户要查看某模块旧日，必须显式进入该旧日视图，不把它拼进 D。全部约定能力均就绪才能标记“全功能完整”；核心就绪而其他能力等待应标记“部分能力待更新”，不能谎称全产品完成。

主日期列表可以列出核心已发布日期，并携带能力矩阵；“可选中 D”不再表示 D 的所有功能已齐全。某模块日期列表按本模块可用性过滤。

### 2.4 终局验收目标

- 相关能力最后一个必要来源实际可用后，95% 正常日于 30 分钟内可见；记录来源可用证据和首次观测时间，不能把粗粒度轮询时间伪装成官方发布时间。
- 不承诺来源尚未发布前的固定更新时间；展示下一次探测和来源等待原因。
- 错日期、伪造零值、重复发布效果、历史恢复导致最新指针倒退：零容忍。
- 连续 20 个真实交易日，无因系统内部缺陷而需要人工补采；外部停源、预算停机仍报告服务影响，不能从可用性报告删除。
- 一次失败后能从最后有效检查点恢复；同一事实不重新全量采集。
- 所有承诺的周期都有真实结果或具体缺口；不能仅靠空态文案宣称历史恢复完成。
- 资源计量覆盖采集、CI、部署、重试、盘点、PCF、页面读取和存储；不以“预计免费”替代事实。

## 3. 终局架构：一个模块化应用，不是更多服务

```text
官方来源（各自发布时间、交易日、修订规则）
              |
              v
       Python 来源适配器 / 规范化 / 模型 / QA
              ^
              | 同一应用执行器；仅执行环境不同
     GitHub 执行环境     本地受控应急执行环境
              ^
              | Cloudflare 主触发 + GitHub 轻量兜底
              | 复用同一 runKey / lease，不能重复启动重任务
              v
 R2：不可变原始证据、规范事实、模型、检查点凭据
 D1：必要索引、投影、租约、发布清单与小型指针
              |
              v
     候选清单 -> QA / canary -> 原子可见清单
              |
              v
     Worker 读取小指针、流式返回 R2
              |
              v
  页面固定清单版本 + 能力/周期状态 + 可追溯详情
```

### 3.1 已有能力与唯一职责

| 复用对象 | 唯一职责 | 禁止再造 |
| --- | --- | --- |
| `adapters/official.py`、`pcf_xml.py` 等 | 来源请求、真实日期和单位解析 | 独立 probe 复制另一套业务日期推断 |
| raw/canonical、source fingerprint | 事实证据与内容身份 | 用任务状态或“最新日期”代替原始事实 |
| `source_observation` | 可回放来源观察 | 第二套通用来源账本 |
| `market_day_state` | 可重新生成的紧凑投影 | 当作可以人工改写的业务真相 |
| `pipeline_window` 及既有 recovery lease | 所有执行环境的领取、续租、完成 | 新建与旧锁不互通的“本地锁/新任务锁” |
| `pcf_capture_job/item` | PCF 逐 ETF 子任务检查点 | 把所有子任务重新塞入总任务 JSON |
| `release_manifest` / `active_release` / slots | 不可变版本与原子可见引用 | 第二张全局 active 表、重复发布服务 |
| read-model builders、canary | 离线计算与消费端证明 | Worker 请求时临时计算或补历史 |
| `trading_desk.cli`、现有 scripts | 一个正式应用入口，scripts 为薄适配 | 再造“只给恢复用”的独立业务实现 |

决策清单优先扩展已有 manifest；它引用精确 capability releaseId/hash，不复制数据。若确需 decision slot，可使用现有表的受控 slot 扩展，不建平行真相层。实现前证明现有结构为何不足。

### 3.2 不做的事

- 不换 React/Vinext、Python、D1/R2，不引入 Kafka、Redis、Kubernetes、微服务或新工作流平台。
- SQLite 可以用于本地测试、缓存或离线计算，但不以“SQLite 免费”为由迁移线上协同与发布。它不能自动解决日期、证据、恢复和运维问题。
- 不永久保存所有中间构建产物；也不未经恢复演练就删除唯一原始证据。
- 不把公开/私有仓库切换当作可用性设计；不在公共 PR 上运行带生产凭据的自托管执行器。
- 不新增实时行情、自动下单或新投资信号；先完成可信日频闭环。

## 4. 数据、时间、身份与发布不变量

### 4.1 四种时间、三种身份

| 字段 | 含义 |
| --- | --- |
| `windowDate` | 上海时区调度窗口日期；只服务调度和 runKey |
| `targetDate` | 明确请求或经正式接口绑定的目标业务日；自动发现前允许为空 |
| `sourceBusinessDate` / `snapshot.asOf` | 原件证明的业务日 / 该能力发布的数据日 |
| `publishedAt` / `observedAt` / `builtAt` | 来源发布时间、首次观测时间、计算时间，分别保存 |
| `runKey` | 调度窗口执行身份；沿用 `daily-market-data:<windowDate>:<window_name>:v1` |
| `sourceFingerprint` | 来源、数据域、业务日期、请求分区、规范身份/原始哈希及合同版本的确定性身份 |
| `releaseId` / 阶段输入摘要 | 模型和可见结果身份，不使用 GitHub run ID 代替 |

约束：

- 原子绑定规则保持：合法 owner、有效 lease、目标为空才绑定；同日幂等，异日拒绝。完成时 `completionAsOf == targetDate`。
- 手工明确目标 D 时，来源只能证明 D 或报告不匹配；禁止自动顺延到最新可得日期。
- 自动发现先用官方交易日/文件业务字段确定待处理日；不能用自然日前一天，也不能用“已成功发布日历”推算相邻份额日期。
- probe 中的候选目标不是日期证明；正式 collector 必须重新验证。
- 修订产生新 fingerprint 和不可变 revision，不改写旧对象；观察时间、runner ID、HTTP Date 等噪声不能单独触发重建。
- 不改写既有已归档 fingerprint 的算法或值。原始字节变化可生成新证据版本，但模型是否重建应比较稳定 canonical 输入与算法版本；probe 的变化提示、原件哈希、模型输入摘要各司其职，不混成一个万能 hash。
- 同一窗口完成后出现来源修订，进入下一个合法窗口或正式修订入口；不改写旧 runKey/target。若现有合同无法表达，单独提出版本化变更，同时升级所有调用者，禁止临时拼后缀制造另一套幂等。

### 4.2 数据可复算与历史窗口

- 股票/ETF 使用带市场的代码身份，名称是可修订属性；不靠名称关联，不丢前导零。
- 分类版本、公式版本、解析器版本、份额/NAV/PCF 日期随模型保存。
- 本轮不借重构改变金额公式。先把现行已批准公式与 `navDate` 固定成 golden fixture；若发现现行公式本身错误，独立行为修复并明确哪些历史需要重算。
- 1/3/5/10/21/63/126/252 个日变化通常需要多一个真实基准快照；今年来按官方日历与年初基准计算，不硬编码为 252。
- 新上市、退出、暂停披露、缺基准、单位调整各自有状态；不能把缺基准设成零。跨拆分/合并等事件按明确合同处理，否则阻断该指标。
- 总览、雷达、轮动必须消费同一版本日变化与样本集合。板块合计 = 已分类合计 + 未分类合计；不要求不同单位或不同可比样本的数值相等。
- 严格窗口缺任一必要节点，严格汇总不可用；允许另列“部分覆盖样本”，但不能冒充全市场完整结果。
- 窗口必须从独立、可追溯的官方交易日证据枚举，再与事实逐项连接；不能对 `state.dates`、已发布日期或现存文件取最近 N 项来代替 N 个官方交易日。日历/业务日证据缺失或冲突时，该依赖保持 UNKNOWN，不用工作日猜测，也不伪称已有官方休市日历。
- `etf_flow_state` 与 `market_day_state` 都是可重建投影，不是事实源。前者缺日、缺市场或损坏时，从经过验证的既有规范事实/原件重放；不能让投影中的空洞改变预期窗口或来源适用集合。具体接入与验收按第 15.11 节执行。

### 4.3 发布、历史登记与最新激活分开

```text
事实已验证 -> 模型已构建 -> 候选 QA 通过 -> 工件完整可读
                                           |
                            +--------------+-------------+
                            v                            v
                       历史版本登记                 最新候选激活
                       可以是旧日期                 CAS / 单调版本
```

- 先写所有不可变工件、校验哈希，再登记 manifest，最后原子切换可见引用。
- 激活前检查 owner/lease 或现有 fencing 代次；旧进程迟到回调不能覆盖新 owner。
- 写成功但客户端超时，先按内容身份/receipt 查证；不能盲目重复生产副作用。
- 旧日期恢复只登记对应历史，不回退 latest。发布任务成功与最新指针是否应变化分别报告。
- 同日修订有显式版本顺序与来源证据；不能仅凭重跑时钟更晚就覆盖可信结果。
- 页面一次会话固定精确清单及其引用；跨版本请求竞态被丢弃，不混合显示。
- “关闭读 flag”并不自动保证安全回滚：必须验证旧读取仍能读同一有效日期/工件；否则保留已固定的最后有效页面，明确错误，不静默切到更旧日期。

## 5. 影子验证：先旁观，再接管

### 5.1 三类开关必须分清

| 现有开关 | 已知作用 | 收敛要求 |
| --- | --- | --- |
| `SOURCE_OBSERVATION_SHADOW_ENABLED` | 原件归档后写 observation receipt / D1 投影 | 纯附加观察；自身失败不新增主链路失败 |
| `MARKET_DAY_PROBE_ENABLED` | 当前会实际决定是否 dispatch | 明确为控制权限，不能称为纯影子开关 |
| `PCF_CAPTURE_V2_READ_ENABLED` | 穿透 API 选择独立 slot | 仅控制读取；不是 XML 采集许可或五日通过证明 |

mode 的目标语义：`OFF -> OBSERVE -> ENFORCE`。不增加一串平行布尔开关。优先在现有配置解析模块增加单一 probe mode，旧布尔值仅作为有期限的兼容输入：旧 0 映射 OFF，旧 1 映射 ENFORCE，不能静默把现有生产控制改成观察。新旧配置冲突必须拒绝并报警。配置迁移、开启观察、开启控制分别记录。

### 5.2 纯观察合同

在 OBSERVE 下：

- 计算并记录 `wouldDispatch`、理由、候选业务日期、旧流程实际决策，不据此取消或增加正式重任务。
- receipt R2 写失败或 D1 投影失败：记录可观测错误，本次观察不计入验收；原有 raw、QA、鉴权、发布合同仍决定主任务成败。
- 只容忍新增观察旁路失败。原始文件缺失、哈希冲突、现有质量门禁失败仍阻断相关能力，不能用“影子不阻断”掩盖事实损坏。
- receipt 失败后依托已存在的 raw/metadata 和有界错误记录重建；不新造无限重试队列。不重采已经确认的官方原件。
- 每次观察有限来源数、字节、时间和 D1/R2 操作；预算不足则跳过观察并保留原因，不抢占核心任务。
- 观察旁路有独立超时和总延迟上界；仅把错误改成非致命但无限等待，仍不满足非干预合同。超时与异步收尾必须能被记录，不能丢弃未完成 Promise 后宣称观察成功。

### 5.3 probe 只能提供提示，不能冒充事实

- HTTP 200 不等于有目标日数据，页面更新时间不等于业务日期。
- 单页/正文前缀不变不证明全数据集不变；抓到“最新一天第一页”也不代表目标日已经完整。
- 不把动态 HTTP header、随机字段或观测时间纳入触发重任务的语义指纹；保留原始响应哈希作为审计证据。
- 切到 ENFORCE 前须有防漏采规则：在有界 reconcile 周期内做必要完整性检查。仅凭稳定 probe 不能永久跳过采集或候选构建。
- `READY_TO_BUILD` 但发布尚未完成时必须允许复用原件继续 build；不能因为来源齐了就从调度入口永久返回。
- 未过期 lease、已完整且相同输入、未到来源窗口，才是明确跳过条件；失败、等待来源、等待预算各自显示下一动作。

### 5.4 五个真实交易日不是五天计时器

协调器观察需满足：相同语义合同下，连续五个官方交易日有真实 observation、预测决策与实际结果对照，无会漏掉必要采集的 false negative，无重复副作用，预算有证据。

- 同一天重跑不增加天数；周末/休市日不计；没有运行就没有观察。
- 未成熟交易日保持待观察，不假装失败或通过；成熟但缺证据不能从列表剔除凑连续五日。
- 改变日期、调度或身份语义后，受影响的观察重新积累；与语义无关的文案/格式修复不自动清空所有证据。
- 历史 fixture 回放能证明逻辑，但不能替代真实来源发布时序观察。
- 观察失败不要求把所有其他工作倒退重做；仅阻断该控制器接管生产。
- 五日只提供有限真实运行证据，不证明所有边界已覆盖；节假日、修订、断电、限流等还必须由集成测试和恢复演练补充。

## 6. PCF v2：独立、精确、有界的穿透证据链

### 6.1 保留的设计

一次官方 XML、逐 ETF 检查点、串行限速与熔断、真实相邻日期、canonical 可复算、穿透独立 slot、分层留存。v2 不是“ETF 全市场真实资金流”升级包，当前来源范围也不能冒充包含所有交易所。

正式 D 日同日篮子模型保持：`TradingDay=D`，`PreTradingDay` 为真实上一交易日，基金代码匹配，申赎单位与成分单位可解释。D+1 PCF 不可改标成 D 的 exact 数据；合法 legacy 估算单独标注，不能混入 exact 历史。

### 6.2 采集窗口与任务独立性

上交所 PCF 网页公布 08:30 统一更新规则。因此：

1. D 日份额可验证后尽早建立计划，晚间先归档 D 日 PCF，不能等待深交所、两融或整个 dashboard confirmed。
2. 下一更新窗口前，仅续跑尚缺的精确项；每个响应仍检查真实 XML 日期，不能假设 08:30 前一定是旧日。
3. 把 PCF 捕获触发从“核心 collect 全部成功”中解耦，但复用现有 PCF job/checkpoint，不另造调度平台。
4. 若 D 日份额长期晚于 PCF 覆盖窗口，不自动扩大到每日全量预采；先测量窗口失配，再提出带成本上界的预归档方案。
5. 历史补采先查精确归档。仅支持当前清单的入口已换日时，记录不可恢复原因；不无限重试，也不顺延目标日期。

`pcf-v2-capture.yml` 当前同时包含 live 当前日期计划和多日期历史验收列表。实施时将“本次要捕获的日期/自动发现”与“要汇总的验收日期范围”明确区分；输入五个日期不能让用户误以为捕获了五天。每日采集成功不应仅因为累计尚不足五天而显示采集失败，分别输出 captureStatus / qualificationStatus。

### 6.3 适用范围与失败归因

事先版本化 eligible universe：市场、基金类型、清单可得性、支持的穿透公式。100% 覆盖指该日计划中全部 REQUIRED，不是事后删除失败 ETF 得到 100%。

至少区分：`NOT_APPLICABLE`、`NOT_YET_PUBLISHED`、`HTTP_RATE_LIMITED`、`TRANSIENT_NETWORK`、`WRONG_BUSINESS_DATE`、`INVALID_XML`、`UNSUPPORTED_SCHEMA`、`SHARE_BASELINE_MISSING`、`BUDGET_DEFERRED`、`ARCHIVE_UNAVAILABLE`。旧报表“105 个不可用”等数量只能作为历史线索，不能硬编码结论。

- 债券/货币/跨境/现金替代不是天然的“抓取错误”；是否支持由产品与来源合同决定。
- 新上市不能把前日份额当作零；缺基准独立披露。
- 份额未变化可跳过只为计算净份额贡献的 PCF 请求，但不能由此声称掌握实际持仓、篮子调仓或毛申赎。
- 403/429 停止当前来源批次并保留进度；退避遵守来源限制，不能更换 IP 绕过。
- 达到 max-items/seconds 产生 continuation，而不是把未尝试项批量标记真实失败。

### 6.4 五日资格与生产读取

PCF 五日证据包括：真实同日覆盖、原件/canonical/manifest 哈希、至少边界样本独立复算、逐 ETF/个股/汇总对账、错误归因、重试资源、从保留证据重建演练。

旧链路不是绝对正确答案。对比差异要区分日期口径变化、旧解析错误和新缺陷；不能为了数值一致保留旧错误，也不能每天重复高成本旧查询。已保存的真实 legacy 工件可复用。

开启 `PCF_CAPTURE_V2_READ_ENABLED` 前，必须证明目标 slot 的 producer/schema/formula/lineage 确实来自验收通过的 v2；开关本身不能充当来源证明。核心市场发布不等待 PCF 五日，PCF 五日也不等待协调器五日。

### 6.5 留存边界

沿用现有 v2 提案：单 XML 30 天、日原始包 180 天、低损失 canonical/manifest/hash 长期保留，核心小体量官方原件另按既有策略。它是目标政策，不是当前 R2 已生效证明。

应用生命周期前必须确认前缀、Bucket Lock、活跃引用、恢复演练与增长预算。新政策不追溯删除旧永久原件；180 天后没有原始字节就不能声称可重新验证原始 XML，只能依据已验证 canonical 复算已有字段。失败、争议或唯一副本在明确处置前隔离保留。

## 7. 一个执行器，日常、续跑和恢复只改变参数

### 7.1 不新造命令体系

在现有 `trading-desk` CLI 下增加 pipeline 子命令或复用既有命令，具体命名在 v0.6 锁定。以下是目标能力，不是现在已经存在的可执行命令：

```text
plan -> collect-missing -> normalize -> build -> verify -> publish -> verify-visible
                    ^                                  |
                    +-------- resume verified ---------+
```

planner 是无副作用函数；runner 调用现有 adapter/builder/QA/发布客户端。YAML 只做凭据注入、安装、调用、上传摘要和平台结算，不再自行推断交易日或拼接恢复状态。

### 7.2 检查点协议

复用现有 receipt/immutable manifest，必要扩展：输入哈希、源日期、解析器/公式/分类版本、producer SHA、输出位置与哈希、验证结果、资源实测、lease/attempt 身份。

- 检查点存在且输入/版本/输出验证匹配才可跳过；“文件存在”不算完成。
- 只重跑变化节点及其下游。来源修订或算法变化按依赖图失效，不无脑重采全历史。
- 运行机磁盘、GitHub artifact 不是唯一持久来源。跨机器续跑从批准的 R2 工件和 D1 小型状态恢复。
- 本地执行和 GitHub 执行使用相同版本、相同 API、相同正式鉴权和预算，不能以“本地不花 Actions”绕过 D1/R2 约束。
- 有效租约由一个 owner 持有；检查点子项不构成另一套不互通锁。断电、超时、续租失败与迟到回调均测试。

### 7.3 何时自动重试，何时停

| 情况 | 自动动作 |
| --- | --- |
| 短暂网络错误/平台执行失败 | 已批准范围和预算内，指数退避、有界重试，从检查点续跑 |
| 来源尚未发布 | 正常等待，到下一来源窗口探测，不启动完整构建 |
| raw 已有而模型/发布失败 | 复用 raw，只重做必要下游 |
| 哈希、日期、单位或模型一致性错误 | 隔离该能力，停止并给出具体证据，不降低断言 |
| 预算不足或账号被限 | 保存进度，停止相关任务；不重复 dispatch，不以旧失败证明新尝试结果 |
| 官方历史已不可得 | 终态缺口说明；有证据变更才重新评估 |
| 需要改代码/新权限/新日期范围 | 独立 PR 或申请新增授权，不在补采中改生产代码 |

受控恢复暂时继续调用现有审批与 receipt 接口；它最终是同一执行器的受限入口，不是独立计算路径。R0-D 仅保留目标级诊断，不成为正常日或续跑前置条件。

### 7.4 主链路完整性与有界对账

主链路先保证本次声明正确，低频对账发现遗漏，恢复入口只处理例外。对账复用现有依赖 planner、runner、租约、预算、检查点和发布客户端，不新增账本、锁、独立修复服务或调度平台。

- 采集/归档完成后：比较本次真实输入、直接基准和已有输出身份；仅计划失效下游，不重复采集。
- 构建/发布前：核对该能力的官方日期集合、市场、样本、输入哈希和实际输出；不能仅凭工作流成功或 quality 总计 pass 声明完整。
- 低频兜底：复用现有 reconciliation 窗口，分批检查获授权的热范围和游标；不得每次请求/轮询扫描 280 日或全桶。先候选/只读验证，再经明确策略授权启用自动写入。
- 自动补算优先于补采；哈希/日期/单位冲突先隔离。只有证明来源缺失且现行范围允许，才进入有界补采。索引缺失先查旧 manifest/receipt，不等于来源缺失。
- 普通重入与历史修复仍遵循各自有效授权；本节不把“继续”解释为新增日期范围、自动历史写入或绕过恢复批准。

实现切片、测试和启用边界见第 15.11 节，不再为此建立第二份路线图。

r6 的交付顺序、整条传输容量预演和失败终态闭合要求见第 15.12 节。日常对账与例外恢复仍复用上述模块，不为“恢复失败后的恢复”再造一套状态系统。

## 8. 资源治理与故障域

### 8.1 计量真相

每项指标保存 `value + unit + basis(measured/estimated/unknown) + measuredAt + scope`。不得默认 0 代表未测量。

- D1：记录实际 meta.rows_read/rows_written；逻辑 changes 与物理索引写入分开。
- R2：区分 Class A/B 请求、字节增量、存量和生命周期，不能只按文件大小算。
- Worker：请求量与 CPU/错误情况；页面轮询也计入。
- Actions：所有 job 的运行量、重试、CI、部署、PCF和恢复；执行时长估计与最终账单分钟分开。
- 本地执行：Actions 可为实测 0，但机器耗时与其他平台操作仍记录。
- 计量本身有上限，按阶段聚合，不为每条证券写一行遥测。

事前 reservation + 执行中扣减 + 事后结算。未收到最终结算的任务保留保守占用，不能释放成零；不同任务的预算领取必须防并发超卖。先复用现有资源账本能力，不另建通用计费平台。

### 8.2 免费是约束，不是保证

数值以 `config/resource-budget.json` 为唯一配置入口，变更有理由与测试；实施时按账户套餐和官方规则核对。D1 逻辑更新一行可以计多行写入，不能重犯 `rows_written > 1` 就拒绝合法 claim 的错误。

优先级：生产最小读取 > 目标日核心采集/发布及必要重试 > 有时间窗口的 PCF 证据捕获 > 近期缺口恢复 > 双轨验收/长历史/冷审计。低优先级不能抢占核心保留量，PCF 捕获与昂贵 parity 区别计费。

账户官方遥测暂不可得时：

- 显示 UNKNOWN；内部账本不是整个共享账户的余额证明。
- 仅当任务成本上界不超过可证明的剩余额度保守下界，或不超过已确认、未被其他任务占用的账户保留预算时，允许相应任务；配置里写“保留量”本身不证明真的剩余。剩余额度的上界不能证明任务一定装得下。
- 无法证明任务成本上界和足够的可用预算时，停止有配额风险的远程重任务，继续本地 fixture/代码工作和允许的有界诊断；不强制生成手工 JSON 假装闭环。
- 不重新把 `FLOW_OFFICIAL_USAGE_EXPORT_JSON` 设为日常人工门票；官方遥测自动取得则复用，不能取得则报告具体未知边界。
- 不声称在未知共享账户状态下能同时保证零费用、永不延迟、全量覆盖。这三个目标存在现实取舍。

### 8.3 减少无效消耗

- CI 基于变更范围运行必要矩阵；关键合同/共享代码仍跑完整相关链路，不为省额度跳过必要验证。
- 对同一 SHA 复用可信构建/测试产物；不能把不同 SHA 的绿色结果移用到当前提交。
- deploy 使用已验证 bundle，若需重新构建须说明并计量；migration 与部署不能因重试无界重复。
- 不为没有新来源、没有待构建工件的窗口安装完整依赖并运行测试。
- GitHub 和 Cloudflare 两个调度器共享同一 GitHub 执行环境，不是执行级容灾。本地受控执行器是应急方式，不是自动运行任意代码的公共 runner。

## 10. 各版本实施卡

### v0.5.1 / PR A：第一项工作，仅修非干预观察

目标：观察机制的故障不新增正常归档失败；不改变任何真实数据门禁。

实施前只做有界代码基线：main SHA、已有相关 PR、schema/flags 定义、调用者、保护路径。能只读取得线上 flags/build 时记录；无法取得只写 UNKNOWN，不为本 PR 创建生产盘点流程。

主要入口：`history-import/route.ts`、`source-observation.ts` 及对应 web tests。保留现有 API/字段，不新增 migration、不修改 workflow、PCF、公式或生产读取。

测试必须证明：

- flag=0 旧行为不变；flag=1 观察成功则写有效证据。
- raw/metadata 已验证成功但新增 receipt R2 失败：主流程按旧合同处理，响应有明确 observation 降级信息，本次观察不能记为通过。
- D1 投影失败同样可识别；重复观察幂等，后续从已归档证据有界补观察，不重抓源站。
- raw 写失败、哈希冲突、日期或原有 QA 错误仍拒绝，不会因宽 catch 放过。
- 日志/响应无秘密；不静默丢掉观察错误；预算上界和重试上界保持。

交付：独立 PR、完整本地测试、CI、实际合并副作用清单。停止于 CI_PASSED，等待合并/部署授权。CI 因额度不能运行就报告 CI_BLOCKED，不把本地结果改称 CI 通过。

### v0.5.1 / PR B：probe 从观察到控制的合同

复用 worker/probe/projection，实施第 5 节模式和日期规则。OBSERVE 下正常 dispatch 决策必须与旧路径等价；仅记录 wouldDispatch。候选 targetDate 与正式绑定严格区分。

覆盖：T 晚间、T+1 上午、周末/节假日、SZSE 发布日与业务日不同、探测 200 空正文、单页不变尾页修订、暂时 404、稳定 fingerprint、READY 但未发布、投影持久化后断电、D1不可用、重复定时器。

预期不需要 migration；若确需持久字段，单独解释兼容性和最小变更。不启用 ENFORCE，不增加生产重任务。部署后经授权开始协调器五日观察。

### v0.5.1 / PR C：PCF 有界捕获闭合

按第 6 节核对已有实现，只修确认缺口：独立来源窗口、捕获日期与资格日期分离、预算暂停不冒充真实失败、适用集合与精确日期拒绝、资格报告增加原件/模型验证引用。不得无证据更改 universe 以便过关。

只有代码 PR，不在 PR 中补历史、启用 read flag 或变更生命周期。部署后才能在授权范围积累 PCF 五日；已有可证明合格的记录可以复用，不因版本编号变化机械清零。

### v0.6：执行器和资源先收敛

- PR A：从当前 collect/publish/recovery 的已测试业务提取共同应用函数；保留薄兼容 wrapper，先无行为变化。用同一真实脱敏 fixture 对比旧/新输入、工件和允许副作用。
- PR B：统一阶段实际计量、UNKNOWN、保守 reservation、预算递减和结算。修掉用量 0 占位；预算本身不得造成全表扫描或高频遥测写入。

验收：任意阶段中断再续跑、两执行环境争抢、租约过期、成功回写丢失、R2 成功/D1 失败、按日期串行、旧历史不回退 latest。Linux CI 与 macOS 本地入口都做 fixture 冒烟；本地 fixture 成功不替代真实生产恢复验收。

### v0.7：能力清单、历史窗口与 UI 候选

- PR A：把第 2 节能力合同固化并版本化；扩展既有 manifest，声明日期、覆盖、原因、准确工件引用。与旧 schema 并存，不修改已发布历史。
- PR B：有界构建每只 ETF 的日变化与周期依赖。优先原始/规范化已有事实；热窗口目标约 280 个有效交易日加必要基准，不用自然日替代。不在代码 PR 中执行生产回填。
- PR C：候选 UI/只读入口固定清单；显示请求日期、实际日期、每能力状态、每周期真实节点数及具体缺口；搜索与详情属于同一发布版本。旧读取仍保持当前生产路径。

历史顺序：最新日及前置基准 -> 近期缺口 -> 两周/一月 -> 三月/六月/今年来/十二月。只对有缺口的依赖重建；每个范围先输出最小计划与预算，不把全历史再采一遍。

验收：同日核心可发布而 PCF/旧长周期缺失；已声明可用的任意能力损坏必须拒绝该候选，不能发布含谎报的清单。可隔离失败能力后重建一个明确标记缺失的新候选，不能原地忽略错误。

单日候选 canary 后积累五个真实业务日对照；不重复采原始来源。候选读取能验证不等于生产已切换。

### v0.8：四个独立生产切换，不打包全开

| 切换 | 必需证据 | 回滚 |
| --- | --- | --- |
| runner 执行入口 | 等价 fixture、命令级集成、续跑演练、单窗口真实 canary、预算 | 停止新领取，处理在途 lease，再恢复兼容入口；禁止双执行 |
| coordinator ENFORCE | 五日 OBSERVE、日期/防漏采验证、误判清单为空 | 恢复 OBSERVE，不删除事实或租约 |
| 核心 capability/清单读取 | 五日候选、UI/日期/历史/ETag 对账、旧读回滚验证 | 恢复兼容读取或固定最后有效清单，不改历史数据 |
| PCF v2 穿透读取 | 五日 exact 资格、slot来源证明、stock search/detail/模型齐全 | 恢复已验证兼容读或明确不可用，不能切入错日数据 |

每次切换先展示实际 flagsBefore/After、SHA、已有 migration、在途任务、预算、停止和回滚条件；授权后才执行。任何一项未通过只阻断该项，不能把 PCF 当作核心日更新前置条件。

切换后连续十个真实交易日验收受影响功能；可与其他独立观察同期，但必须是对应配置实际运行证据。只读验证失败不能连续点击重跑任务，应先定位已写副作用。

### v0.9：历史债务和兼容层退出

两类工作分开：

1. 有界热历史恢复：利用现有索引与 manifest，按日期×来源×raw/canonical/model/visible 分级。只补必要缺口；修订会重建受影响下游。不可恢复日期明确列出，不伪造现代 metadata。
2. 路径退役：按第 11 节逐项删除，无需等整个冷历史完整。全范围 R0-D 退出正常路径，只保留一个有界诊断入口和必要取证能力。

冷归档采用 VERIFIED_MODERN / VERIFIED_LEGACY / RECOLLECTABLE_MISSING / UNVERIFIABLE_LEGACY / OFFICIAL_UNAVAILABLE 等既有分类，不要求所有旧日期达到现代合同才允许新日更新。

历史交付分别报告：已修复、仍可修复且待预算、官方不可恢复、证据不足待核查。只要范围内可恢复缺口尚未处理，不能把“有空态提示”当作历史恢复完成。

### v1.0：签收而非再新增一层系统

在主读取、主执行配置稳定后积累连续 20 个真实交易日证据，核对第 2.4 节 SLO、预算、功能周期覆盖和退役清单。外部原因造成的不可恢复历史单独验收，不伪造；不得把已承诺但仍可恢复的长周期缺口藏在 DONE 中。

终局运行手册只保留：正常运行、来源等待、按日期诊断、批准范围内续跑、质量隔离、读/执行回滚、凭据轮换、预算暂停/恢复、备份恢复。新增业务功能只能在相应基础能力稳定后另提需求。

## 11. 退役清单：保留什么，删除什么

| 机制 | 处理 | 退出证明 |
| --- | --- | --- |
| 原始证据/hash/精确日期/质量校验 | 永久保留原则 | 不因收敛删除 |
| pipeline lease、PCF item checkpoint | 保留并明确上下层 | 无重复锁、实际 owner/fencing 测试 |
| observation、market-day projection | 保留；一个是证据，一个是派生 | 不能把投影状态变成另一份真相 |
| `daily-data.yml` compatibility wrapper | 退役候选 | 所有调度/API/人工入口迁移，观察期无调用 |
| collect 中非 delegated 的重复发布分支 | 转为同一应用函数后退役 | 等价与续跑验收、无旧调用者 |
| 独立 recovery 计算实现 | 收敛为统一执行器适配 | 真实受控恢复同合同验收，不是只测普通任务 |
| 重复 inventory/preview/provenance repair 工作流 | 合并为一个有界诊断入口 | 使用者清单、输出兼容、必要修复权限保留 |
| mutable latest 文件跨任务传递 | 改为不可变引用后删除协议 | repo 的用户 reports/latest 文件不在删除范围 |
| rolling state 充当日期/完整性真相 | 改为有输入身份的可重建缓存 | 日历缺日、缺市场、缓存损坏的重放与旧读回滚验证；旧缓存按引用保留，不自动删除 |
| manifest v2/旧slot生产写路径 | 先停写，再删无人使用代码 | 旧历史读兼容仍有使用时保留只读适配 |
| 旧布尔 flags/新模式兼容 | 设置截止版本并移除 | 配置、脚本、运行手册无引用，线上有效配置已验证 |
| 过时 README 和互相覆盖的 runbook | 更新唯一当前运行说明，旧handoff标历史 | 不删除用户未提交文档；单独授权纳入文档维护 |
| R2旧对象、D1旧表、worktree目录 | 不随代码退役自动删除 | 独立数据保留/备份/恢复验证和明确删除授权 |

每个退役项有 owner、调用证据、替代路径、观察截止、回滚办法；删除代码用独立 PR。不要因为搜索不到字符串就断言没有外部调用。活跃凭据和历史读兼容不能随便清理。

## 12. 测试计划：测完整行为，不只测字符串

### 12.1 行为覆盖图

```text
官方 fixture / 实际来源证据
  -> 日期/单位/代码验证 [单元：正确、错日、新上市、单位变更]
  -> raw/metadata归档 [集成：重复、冲突、超时结果不明]
      -> 观察旁路 [集成：R2/D1失败不新增主失败；原QA仍有效]
  -> 计划/租约/预算 [并发：唯一owner、过期接管、预算不足]
  -> build [确定性：输入变更只失效下游、长周期缺口]
  -> candidate [合同：能力声明与实际工件一致]
  -> publish [集成：部分写入、迟到回调、原子可见]
  -> API [集成：精确日期/slot/hash/ETag]
  -> 页面 [E2E：搜索、周期、下钻、刷新竞态、缺失解释]

```

此图是必须补齐的验收路径，不是当前已通过覆盖率报告。实现者必须逐条映射现有测试；缺口新增行为测试，不复制整套测试目录。

## 13. Git、授权、部署与迭代纪律

### 13.1 工作区与PR

1. 原仓库只读记录 `git status --short --branch`、`git diff --name-only`、`git worktree list`。
2. `git fetch origin --prune`，确认main；从它建立新独立worktree和 `codex/<version>-<purpose>` 分支。
3. 路径冲突换新路径，不删除未知目录；不在原脏工作区切分支、rebase、cherry-pick。
4. 一个PR一个可验收目的；结构提取、行为改变、生产切换和破坏性清理不能混为一个目的。
5. 超过8个业务代码文件是范围复核信号，不再机械要求“跨两个层就停”。若端到端同一合同必须同时改调用端与服务端，应说明必要性和原子兼容策略；不得为凑文件数留下半个功能。
6. 只暂存明确文件；禁止 `git add .`、`git add -A`、`git stash`、`git reset --hard`、`git clean`。
7. 不触碰 `reports/phase0/latest-*`、`memory/` 和已有用户未提交文件；旧handoff只读，除非用户另外授权修改。
8. 不提交缓存、全量原件、运行Secrets、Token或Cookie。运行报告进指定artifact/R2目录，不覆盖受保护latest文件。
9. 前一PR合并后fetch，下一PR从最新main开始。事实变化只重新评估受影响范围，不盲目重做所有阶段。

### 13.2 副作用清单必须基于实际工作流

基线中 `deploy-worker.yml` 会在相关PR合并关闭事件后执行 web测试、`wrangler d1 migrations apply flow --remote` 和 Worker部署。因此，“只合并”不等于“无生产变化”。实施时重新读取workflow，不沿用本文静态结论。

合并前一次性列出：确切SHA、CI结果、触发事件、待应用migration清单/SQL、flags变化、自动任务、凭据依赖、资源上界、回滚与停止条件。未知副作用不能先合并再补说明。没有新增migration时核对已应用记录，不运行重复大扫描。

不触发额外CI来“看看额度有没有恢复”，除非该次运行已在授权与预算内；旧运行失败不能证明新环境仍失败。构建身份和数据发布身份分别验证。

### 13.3 一次范围授权，阶段内自动推进

未来已实现的执行器可用以下授权包，取代每个接口都问一次；现有审批协议未收敛前仍依法走现有接口，不直接绕过：


### 15.7 v0.9 至 v1.0：历史修复、路径退出与产品签收

### 15.9 每轮结束与下一轮的固定行为

每轮按第 14 节给短报告，最后固定给出以下内容：

```text
本轮完成：阶段 ID + 可验证结果（不是笼统 DONE）
当前未完成：代码 / CI / 部署 / 观察 / 数据 / 产品验收分别列出
下一动作：明确入口、阶段 ID、范围与所需前置
能否自动继续：能，则继续当前授权范围；不能，则仅列真正阻点
需要你做：无，或一个完整且最小的授权/登录/取舍动作
```

收到已请求的授权后，实施者先完成该动作包并验证；前置满足便按本节继续，不要求用户再把下一阶段的要求粘贴一次。用户只回复“继续”时，读取现有交接块与实际状态即可接续；换任务/换模型也遵循相同规则。

若任务需要等待未来交易日，但没有已经启用的自动监控机制，明确保存停止点。总指令解决的是跨轮次交接，不代表模型会在对话结束后自行后台执行。真正的自动运行必须由已授权的调度/监控机制负责。

**停止询问“下一轮提示词是什么”；改为自行给出“当前已验证到哪、下一动作是什么、是否只有一个明确授权阻点”。整条路线的任务说明已经一次交付，后续不再依赖用户充当人工调度器。**

### 15.10 2026-10-11：080 执行收敛修订（保留合同，当前入口见 15.12）

#### 15.10.1 修订目的、优先级和不变项

将剩余 runner 工作从“逐个辅助函数合并”收敛为三个可验收目标：**完整候选任务闭环 → 正式受控入口 → 一次真实有界 canary**。这是验收目标，不承诺恰好三个 PR，也不把三个目标塞进一个 PR。

本节仅覆盖 080 剩余工作的组织、入口验收、整任务预算和状态报告；与原文这些条款冲突时，以本节为准。版本顺序、真实日期与来源、精确 hash/身份、QA、既有认证和恢复审批、原子租约、免费资源边界、生产授权、保护路径及兼容层退出条件全部保留。不得因此开始 v0.9、删旧系统、关闭门禁或切换生产读取。

正常日频更新和已有有效恢复不等待新 runner。最新日故障仍按第 0.4 节单独处理；不能把“候选 runner 未完”变成停止现有采集的理由。PCF、协调器、核心三条真实观察仍分别验收，已有兼容证据不清零。

**本轮不做：** 新账本/锁/调度平台、重新全量盘点、历史全量补采、PCF v2 扩范围、生产开关切换、兼容层删除、R2/D1 清理。它们不是闭合当前候选入口的前置条件；确有新的安全合同缺口时，给出具体证据及最小拆分，不顺手扩大任务。

#### 15.10.4 `080-FLOW` 的完整调用合同

复用已有 API/状态语义，不额外发明一套任务状态。首次业务副作用之前，任务整体必须获得共享预算准入。为了取得准入而必要的有界读取、claim、预算控制请求也计入任务上界，不能写成“免费前置操作”。

```text
校验请求 / 代码SHA / 锁文件 / 日期与输入身份
  → 从实际阶段、适配器和续跑计划推导完整成本上界
  → 验证现有授权及唯一有效 lease
  → reserve（共享原子预留成功）→ mark_running
  → 每阶段：校验/续租 → 业务执行 → 验证工件
             → 保存可信检查点 → 有界聚合 debit
  → 构建并验证候选 manifest / QA（不激活 latest）
  → settle：成功或已知失败按实际结算；结果不明保留占用
  → 报告任务、预算、工件、owner 与未做动作
```

具体要求：

1. 只复用共享应用和现有 collect/build/verify/publish 适配器，不在 CLI/YAML 重新写业务公式、日期选择、恢复审批或质量判断。候选发布严格限定现有候选权限，不能默认激活。
2. 由真实工件确认 targetDate；windowDate/runKey 不随结果改写。历史登记不回退 latest；缺某能力如实给出状态，不借小样本 fixture 宣称全市场完整。
3. 所有产生业务副作用的阶段都必须位于同一任务预算中。reserve 未获准不得采集、上传业务候选或发布；进入 RUNNING 后才执行业务阶段。复用原子阶段准入能力，不能只在入口检查一次。
4. stage debit 使用现有可信计量与有界聚合，控制请求自身的费用也包括在内；禁止为每行数据/每次 HTTP 再递归发 debit，造成计量调用无限膨胀。阶段失败、计量失败和控制请求失败均计入已发生消耗。
5. 中断重入使用相同任务/操作身份及累计预算，不重建一份可重复消费的 reservation；合法新 owner 通过正式接管后从已验证检查点续跑。不得自动归零计量或重复执行已完成副作用。
6. 响应丢失先按既有 operation identity/回执做有界 read-back，不盲目重复写。无法确定结果时保留 `UNKNOWN` 和预算占用，走现有正式对账；不能因超时、进程退出或租约到期自行释放潜在已消费额度。
7. 续租失败、审批撤销、过期/迟到 owner 必须停止后续副作用。结算同样遵守既有服务端 owner/lease 规则，不能借 finally 绕过鉴权或伪造已结算。
8. 普通与恢复模式共享以上合同；恢复另外核对 planHash、recoveryId、批准范围、真实数据日期和正式租约，禁止绕过审批或另建“恢复预算/锁”。

#### 15.10.4a r4：预算任务身份、原子接管与版本复用

以下修订属于 `080-FLOW` 同一可验收目的，允许在现有共享账本、服务端接口、客户端与编排中补齐。它不是修改生产状态、迁移历史预留或执行恢复的授权，也不另设一次文档批准门票。实现前核对当前 main；已有等价实现则复用。

**一、业务预算身份与执行权限分离。**

- 同一业务任务的预算身份必须稳定，不含 leaseOwner、attemptCount、随机运行 ID 或观察时钟；绑定现有 runKey、真实 targetDate 及必要的输入/合同身份，恢复任务另绑定 recoveryId、批准 planHash/scope。复用既有 canonical 身份语义，不为了稳定 ID 另造来源 fingerprint。服务端推导或验证身份，不能让调用者任意选 taskId 复用别人的额度。
- owner/attempt 仍是当前执行权限，不是预算重置键。增加现有账本上的原子接管能力：仅当前有效且获批准的新 owner 可以接管同一任务，提交条件同时核对账户 revision、当前 lease/attempt 和恢复范围；并发只有一个可获执行权限，旧 owner 不能继续授权、写入或结算。
- 接管原有 reservation，继承完整 cost、authorized、consumed、pending/回执与结算状态；不创建可重复消费的第二份预留，不重置累计量或恢复计划总上限。已完成任务不得重新执行，OVER_BUDGET 不自动解除，UNKNOWN 不因新 owner 或 lease 更新自动变为 RUNNING。未知操作先按可信回执和精确工件有界核对，不能把旧授权回放当作新副作用许可。
- 沿用现有持久化/检查点设施保存未确认操作身份；进程重启不能只靠实例内存重新生成 operationId。跨 owner 核对历史回执与授予当前执行权限是不同动作，不得篡改旧请求的 owner/hash 假装同一次操作。
- 新合同须明确版本/兼容入口及默认行为，覆盖旧客户端回归。不得静默重新解释已有 reservation key、自动改写生产历史行或批量搬迁旧状态；若需要 additive schema 变更或部署，其 SQL、兼容影响和实际合并副作用随同一 PR 披露。

**二、先复用已返回 revision，不先建设批量授权机制。**

- 初始有界 GET 获取 revision；每次成功 POST 后使用经验证的服务端返回 revision 作为下次条件更新的版本。缓存仅是并发控制提示，不是额度或权限证明；服务端最终 CAS 与 owner/lease/批准检查必须保留。不能在客户端自行假定 revision 加一或无条件更新。
- 明确的版本冲突可在硬上限内重新读取并重评准入；保持同一逻辑 operationId，不进入无限重试。超时、响应丢失或不明确错误保留 pending/UNKNOWN，先核对同操作回执，不创建新授权。回放授权不能再次用于执行业务 I/O。
- 按先前的 18 次预算操作示例，正常无冲突路径可由 36 次预算 HTTP 请求降为初始 GET 加 18 次 POST，即 19 次；该数字不包括额外阶段、接管、租约、心跳、检查点、读回或故障处理，不是整任务验收承诺。`require_request_capacity` 与 preflight 必须同步采用实际策略，不保留“每次授权固定两请求”的过时假设。
- 第一选择不是一次发放大量可重复使用的授权，也不是删除逐副作用准入。只有完整测试证明仍有实际瓶颈且现有最小方案不能闭合，才提出具体的最小协议差异；不得顺手建立第二套额度令牌/账本。

**三、全调用图验收后才能宣称冲突已解决。**

- 分别核对 budget、lease、candidate/checkpoint transport 的内部限制，再汇总共享平台成本；不能把预算客户端低于 32 当作租约或整任务也低于 32。
- 客户端检查只有在对应服务端提交路径已有等价有效 fencing 时才可减少；R2 操作不能因旁路预算 CAS 成功就被当作与 D1 原子提交，结果不明仍按既有 immutable intent/read-back 处理。不得一概删除上传前后确认或精确工件读回。
- 将首次运行、新进程续跑、合法 owner 接管、CAS 冲突、响应丢失和尾部结算均纳入有界成本模型与集成计数；对账户遥测未知仍 fail closed，不以估算余额冒充实测。
- 若去掉有证据的重复请求后完整合法包络仍超过内部限制，依第 15.10.5 节给出推导的旧/新请求上界、最大尝试/运行时长及免费资源准入证据，再修订内部限值。禁止仅把 32 改成 64 来让测试通过；调整内部限值不代表提高平台配额、付费限额或获得真实运行授权。

#### 15.10.5 整任务资源验收，不再围绕局部 32 次循环优化

`32` 是现有客户端/lease 的内部请求安全上限，**不是 Cloudflare 免费额度**。第 8 节的账户准入仍有效。既不能为了通过测试盲目提高 32，也不能只证明两个检查点低于 32 就把任务标记可运行。

在现有预算/preflight 结构上推导并输出整任务资源清单，至少覆盖：

- claim、授权检查、绑定/完成证明、续租、状态读回；
- reserve、mark_running、阶段准入、debit、settle、重复请求/read-back；
- 官方来源请求及退避重试、归档读取、构建/QA、候选登记、检查点/接力工件；
- D1 物理 rows_read/rows_written、R2 Class A/B/字节和留存、Worker 请求/CPU、Actions 所有 job/依赖安装/排队后的实际运行、CI/部署共享账户消耗；
- 成功路径与批准的失败/中断/续跑包络，明确最大尝试、最长运行和续租上界。

每项有 value/unit/basis/time/scope；估算是成本上界，不冒充实测。请求数来自当前实际调用图和 adapter/阶段计划，并由完整集成测试的计数校验；不能由调用者任意填写几个小数字来通过准入。入场读取/预算控制/尾部结算的开销预先计入，不能在业务消耗后才发现没有额度结算。

同时校验各现有内部上限和账户保守可用预算。缺账户遥测/有效预留证明仅阻断真实运行，不阻断本地闭环与命令测试；不得伪造 `FLOW_OFFICIAL_USAGE_EXPORT_JSON` 或另设人工 JSON 门票。如果完整上界确实超过内部上限，先缩小真实任务范围、采用既有安全批次或去掉有证据的重复调用；仍需改限值时，单独说明旧/新上界、免费预算、故障包络和兼容测试，取得相应代码/运行授权，不能偷偷放宽或无限追加局部优化 PR。

`server_fenced_checks` 只在能证明对应服务端最终条件更新仍校验有效 owner、lease、恢复批准与预算状态时显式使用。保留旧策略回归；它不自动减少检查点、候选发布或其他写操作的保护。

#### 15.10.6 交付测试：一个完整调用，而不只是很多单元测试

复用现有 test fixtures 和测试框架，补足以下纵向集成验收。使用真实 runner、客户端序列化与本地 HTTP/SQLite 测试服务，实际执行生产同源的适配器和验证路径；故障可在测试边界注入。不得 mock 掉所有控制/预算调用再声称链路通过，也不得把本地模拟服务说成真实 Cloudflare/GitHub 验收。

| 场景 | 必须验证的最终结果 |
| --- | --- |
| 一个核心普通候选任务 | reserve → RUNNING → 阶段/检查点/debit → QA/候选 → settle 完整发生；真实数值/日期/hash 可对账；active pointer 未变 |
| 准入不足或必要预算 UNKNOWN | 不发生业务副作用；保留具体阻因，不能填 0 或估算余额 |
| 每个既有阶段边界中断后续跑 | 新执行环境校验同身份工件，正式 owner 接管；已完成业务效果不重做，计量不归零、不超卖 |
| 同业务任务换 owner / 并发接管 | 只有当前合法 owner 可继续；同一 reservation 的预留、授权、已消耗及 pending 延续，旧 owner 被拒绝，恢复总上限不再预留一份 |
| revision 复用、并发修改与跨进程 pending | 成功回执版本用于下一操作；冲突仅有界核对；丢失回执保留原操作身份；回放不能发放第二次执行许可；旧客户端兼容行为不变 |
| 预算或 R2 写成功但响应丢失 | 通过同 operation/hash 做有界读回；结果不明保留 pending/UNKNOWN 占用；不重复发放预算或伪造成功 |
| 运行中 lease 到期/续租失败/审批撤销 | 后续副作用被拒绝，迟到 owner 不能写/结算；留下可恢复状态及已发生消耗 |
| 工件日期、SHA、hash 或 QA 不匹配 | 候选被拒绝；latest/历史有效版本不受影响；失败仍进入预算处理 |
| 同一编排中的恢复任务 | 正式批准计划与正确 recoveryId/date/范围通过；错误/过期/缺批准被拒绝；普通许可不能代替恢复批准 |
| 完整成功与批准故障包络的成本 | 计数包括控制面、read-back、renew、尾部结算，观测不超过推导上界和现有内部限值；两种检查策略均有回归 |
| 正式入口 | Linux/macOS 命令级调用相同应用，校验固定 SHA/锁、显式模式与凭据来源；fixture/dry-run 无远程副作用，真实模式不能消费伪造成功回执 |

阶段测试图：

```text
入口身份失败 → 拒绝（无业务副作用）
准入失败/UNKNOWN → 停止（保留原因）
准入成功 → 执行阶段 → 工件/QA通过 → 候选完成 → 已知计量结算
                    ├→ 已知失败 → 停止后续阶段 / 已发生消耗结算
                    ├→ 写入结果不明 → 有界读回 / UNKNOWN占用
                    └→ 中断或失去lease → 禁止迟到写 / 合法接管后续跑
```

每个实际新增/变更分支都要有相应行为测试；复用已有覆盖，不为表格再复制一套测试。运行第 12.3 节真实存在的完整 Python 与 web lint/test 链路，核对当前 package scripts；新增集成与命令级用例同时纳入 CI。不得以测试总数、字符串匹配或 fixture 的 COMPLETED 替代上述验收。

#### 15.10.7 `080-ENTRY` 与真实 canary 的安全边界

- 正式入口基于已合并的 `080-FLOW` 装配可信适配器，不能让用户输入任意 Python 类/模块或可执行代码。CLI/workflow 只校验并转交同一请求，业务状态机不重新长回 YAML。

#### 15.11.3 构建与发布的闭合谓词

复用并接通现有 planner → builder → QA → manifest；不能只在工具中生成正确计划，而实际 materializer 继续以缓存日期切片。

```text
官方交易日证据 + 能力适用范围 + 精确来源/revision
                      |
        枚举预期日期/基准并连接已有事实
          ├─ 缺事实/证据不明 -> 具体缺口，不触发无界抓取
          └─ 事实已验证 -> 日变化 -> 受影响周期 -> 候选 QA
                                                      |
                                      精确工件/能力声明一致
                                                      |
                               获授权登记/激活；否则仅 stage
```

1. 对 D 的周期先取得 N 个官方日变化及基准日；YTD 使用首个官方年内日及年初基准。保存 calendar 来源/覆盖/哈希与确切预期日期集合，再连接事实。证据缺失、分页不全或来源冲突不能填成“闭市日”；日历范围外单独 UNKNOWN。
2. 按市场分别核对当前事实与相邻基准；当天数量缺口、重复代码、日期/单位冲突必须可见。D 的 SSE 事实先归档不等于 `etf_daily_core` 已就绪；该核心仍须满足第 2.3 节 SSE+SZSE 合同，不用 SSE-only 偷换完整核心。其他能力按自己的合同独立推进。
3. 每周期报告预期日数、已验证日数、缺失日期×市场、适用/可比样本及指标状态。单只 ETF 缺任一必要变化值，该周期仍为空；聚合只含合同允许的完整可比样本，并披露分母/数量。样本覆盖与“所有官方日期有证据”分别检验，不能用非空总和或阈值掩盖整市场缺失。
4. 新上市、退出、公司行动、无前日代码各按现有显式规则；缺前日代码不自动等于新上市。份额窗口与逐日同日 NAV 金额覆盖分开，不借重构改公式、分类或改为首尾差来绕过逐日依赖。
5. 既有 raw/canonical 通过身份/版本/输出核验就直接复用；来源修订只失效确切受影响日变化及后续窗口，共用节点只计算一次。不每轮下载 252 日事实，也不重新构建未受影响能力。
6. 重放必须经过与普通任务相同的 producer/验证器。同输入重入不重复上传或追加日变化；不在旧 state 数组上盲目 append/累加。输出已写但 receipt 不明，使用现有 operation/hash 读回和 UNKNOWN 占用。
7. 发布前核对实际输出与每项 READY 声明：缺一官方日但缓存仍有 N 个旧值、缺市场但总计 pass，均不能过关。缺长周期不阻断已满足合同的 D 日核心；错误声称 READY 的候选必须拒绝，隔离后生成诚实的新候选，不在原 manifest 上涂改状态。
8. 本节是目标合同，不直接更改当前 v2/v3/schema-v4 激活限制。必要生产兼容修复按第 0.4 节独立交付；候选合同和生产切换分别批准。旧日登记不退 latest；同日修订沿用明确版本/来源规则，不能依靠新时钟抢覆盖。

#### 15.11.4 对账与自动修复的权限、成本和停止条件

对账是现有应用中的有界计划/执行模式，不是新的通用维修系统。复用既有来源索引、旧 manifest 兼容、依赖 planner、runner 和恢复审批；临时离线脚本只作为待审查原型，不直接变成正式旁路。

| 证据结果 | 默认动作 | 必须停止/保留的边界 |
| --- | --- | --- |
| 来源与模型输入未变，输出有效 | 幂等跳过；不再安装重依赖/抓源 | 跳过理由须基于已验证输入/输出，不仅是 COMPLETED |
| 规范事实存在，模型缺失/缓存失效 | 从最近有效检查点定向补算 | 不顺便重采、重建所有历史或自动激活 |
| 对象存在，索引/receipt 缺失 | 精确旧清单查证，必要提出有界元数据修复 | 不手工造 READY 或推断来源缺失 |
| 来源尚未发布 | 等合法窗口，保留已到齐市场事实 | 不用定时重构代替来源等待 |
| 来源确实缺失且可再取 | 仅在有效采集/恢复范围内有界补采 | 403/429、错日、预算上限立即停止相关批次 |
| 日期/hash/单位/独立对账冲突 | 隔离并停止受影响输出；保留最后有效版本 | 不自动覆盖证据、降低断言或不停重试同一坏输入 |
| 状态/写入/账户预算不明 | 有界查证，保留 UNKNOWN、占用和游标 | 不释放成0、不换 taskId 重新领取、不阻塞无依赖本地工作 |

接入时点：本次归档/来源修订后做增量依赖核对；构建前核对直接基准；发布前校验声明；现有 reconciliation 窗口做低频漏失检查。相同业务范围与输入必须跨调度器去重，租约有效不抢占，过期走正式接管。新的输入修订使用现有合法身份/窗口，不随意另拼 runKey。

自动写入启用前，提交**一份有限策略授权包**：允许的滚动热日期规则/来源/能力、只补算还是允许补采、历史登记与最新激活权限、固定代码/合同、每轮和累计资源上界、核心保留量、最大日期/对象/字节/时长/尝试、触发频率、游标续跑、截止/复审条件、质量隔离与禁用/回滚入口。数值由当前调用图和真实预算推导，纳入现有资源配置，不在文档随手指定一个“免费安全数”。包内合规自动动作不逐次问用户；本修订不等于包已批准。

默认只生成候选/只读计划。未批准新定时器就不新增 schedule；正常已授权任务保持原行为。不能开启通用任意日期写入、自动批准历史恢复计划、扩大付费额度或移除恢复开关。现行恢复协议不支持策略授权时，先通过最小代码 PR 收敛，再启用，不能文档先行绕过接口。

| 操作结果或实际计量不明 | 有界精确读回，保留原操作身份、UNKNOWN 和占用 | 租约过期、零 debit、进程退出都不证明零消耗；不换 taskId/planId 重新领被占额度 |
| owner/审批失效 | 停后续副作用；需要时正式接管，继承累计预留/消耗/pending | 不让旧 owner 迟到写入/结算，不以 finally 绕过批准 |
| 日期/hash/QA 或能力声明冲突 | 隔离受影响能力，保留最后有效版本，明确缺口 | 不降低断言、复制他日、补 0 或用更晚运行时钟抢覆盖 |

业务阶段完成、候选已验证、预算已知结算、页面可用是独立结果。若业务阶段完成但计量仍未知，保留对应阶段证据，任务仍不能写作 `CANARY_PASSED`/完整完成；不为绿色状态强行释放占用。若现有正式核对/结算接口不足，指出具体缺口，在同一场景的最小代码修复中闭合，不以直接 SQL 修状态。

一个任务的 UNKNOWN 不自动阻断全部产品工作；其他无重复副作用的任务只有在现有账本仍保留所有相关 UNKNOWN、并能证明剩余预算与权限足够时才可继续。代码修复可能需要新 planHash，必须保留旧计划/占用关联，不能用新身份绕过未核实消耗。无需先清理全账户所有历史状态才做无依赖本地工作。

#### 15.12.6 资源与授权一次闭合，减少人工往返

沿用第 8、13.3 节及现有服务端协议。优先自动取得现有官方遥测；已有证据仍在有效期、范围与合同内可复用。四舍五入、订阅周期和遥测延迟如实标注；消费上界/可用下界有证据才能准入，UNKNOWN 不填 0，不把配置上限当余额。不要求用户手写官方用量 JSON，不为一次缺遥测新增永久平台。

真实动作只提出一个完整有界包：目标日期/来源/能力与精确输入、固定 SHA/合同、正常/续跑/历史登记/最新激活中明确允许哪些动作、全任务和累计资源上界（含预演/安装/控制/失败/结算）、最大尝试与时长、有效期、在途与 UNKNOWN 处理、停止和清理条件。生产字段尚不明确时先做授权范围内准备，不索取未知费用/无限日期的空白批准。

已批准的幂等步骤与明确列出的有界续跑连续执行，包内不重复询问。只批准一次运行就只运行一次；剩余预留包络不能自动变成第二次 dispatch 许可。新代码/范围/风险或过期批准需要重新确认；仅因聊天换轮次、文档措辞修改不作废原本仍有效且语义未变的批准。临时开关在成功/失败/中断后恢复并读回验证；清理不能抹掉 UNKNOWN、已写事实或恢复证据。
