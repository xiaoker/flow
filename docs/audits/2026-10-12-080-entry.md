# 080-ENTRY: one trusted candidate entry

This stage connects the existing runner. It does not claim a production canary,
change a scheduler, claim a lease, enable recovery or activate a release.

## Cost contract

`resourceAccounting.candidateEntryPolicy` is a reviewed conservative estimate,
not official usage or proof of account capacity. The exact task vector is derived
by `candidate_task_cost_upper` from the existing typed request profile, actual
artifact count, control/transport components and runtime. Caller JSON cannot
replace this policy. The shared server ledger still rejects unknown, stale or
insufficient account evidence and approval limits. Missing physical measurements
retain UNKNOWN and the reservation, even if the candidate itself is STAGED.

The scope is three fixed core stages, at most 20 artifacts, fresh attempt 1 or
an explicitly retained second-attempt handoff. No source collection is included.
Request envelopes include confirmation, heartbeat, CAS refresh, ambiguity
inspection, checkpoint readback and terminal settlement. Resume includes both
attempts without a second independent allowance. The first reservation already
includes the complete two-attempt envelope; takeover requests the same total,
never an enlarged cost or new grant. Internal per-attempt request caps still use
the corresponding fresh/resume profile, not the cumulative reservation ceiling.

Per-request bounds used for both ordinary and recovery variants:

| Client | D1 read/write allowance | R2 A/B | Stored bytes |
| --- | --- | --- | --- |
| Lease | 32 / 32 | 0 / 0 | 0 |
| Shared budget | 16 / 2 | 0 / 2 | 0 |
| Candidate | 64 / 3 | 3 / 24 | 1,569,632 |
| Checkpoint | 16 / 0 | 1 / 3 | 1,048,576 |

These are deliberately worst-operation estimates, not minima or observed fixture
counters. Every request includes one incoming Worker request. Core build and
verify are local-only; publish transport/control costs are counted separately,
not hidden in a zero stage component.

D1 derivation: exact primary-key probes (pipeline run, recovery ID, release ID,
account scope) and indexed correlated EXISTS; no list/scan. Allow two row/index
entries per probe. The lease allowance covers 16 probes including renewal batch
guards and readback; its write allowance covers both rows and their maintained
indexes, using the existing recovery renewal's 32-write acceptance ceiling.
Budget covers eight probes including both fenced reads and the atomic CAS; its
single account update has a table entry and primary-key entry. Candidate allows
32 probes including all pre/post-effect confirmations, recovery recheck after
plan read, the final fenced insert and saved-row check. Its only D1 write is the
release row, primary key and as-of index. Checkpoint allows eight probes, including
all recovery confirmations and the bounded immutable plan read; it never writes
D1. Queries are in `pipeline-window.ts`, `pipeline-window-recovery.ts`,
`pipeline-shared-budget.ts`, `candidate-upload-authority.ts` and
`pipeline-checkpoint-object.ts`; indexes are in `web/db/schema.ts`.
This estimate assumes those reviewed indexed query/index contracts. New queries,
indexes, loops or retries require re-evaluation, not silently raising a ceiling.
Provider counters are not reconstructed from SQLite logical changes.

R2 derivation: final candidate request can put intent + artifact + manifest (3 A),
read back artifact + manifest, HEAD all 20 artifacts and HEAD+GET recovery plan
(24 B). Stored bytes are artifact cap 1,500,000 + manifest cap 65,536 + intent cap
4,096. Non-final requests use the same conservative allowance. Checkpoint puts
at most one 1 MiB object and reads it plus HEAD+GET plan. Budget recovery reads one
HEAD+GET plan; ordinary mode over-reserves these operations. Byte vectors represent
new storage allocation, not transfer traffic.

Actions runtime reserves the complete manual job's 10-minute timeout, including
checkout, installation, source preparation, graph derivation and tail work.
Second-attempt policy includes two jobs (20 minutes). GitHub source preparation
is at most three reads, 20 seconds each, and a 6 MiB archive; it adds no D1/R2
writes. It is included in whole-job runtime, not described as free work.
Other PR CI/deploy jobs are not this candidate reservation and must be disclosed
separately before those actions. Local execution uses the same conservative policy;
this does not imply local processes consume Actions minutes.

## Commands and input contract

Fixture remains the default. Dry-run checks declared identity/locks, does not
contact servers or write checkpoints, and returns DECLARED_INPUT_CHECKED, not a
grant. Candidate uses fixed adapters, exact checkout SHA, clean tracked code,
the lock digest, pinned snapshot hash/date and environment-only credentials:

The candidate runtime is CPython 3.12 plus the complete 19-package pinned closure
in `config/pipeline-python-runtime.lock`. Install that file with `pip install
--no-deps -r ...`, then execute the checked-out source via PYTHONPATH; do not use
unconstrained editable installation in the manual job. Candidate entry requires
both this lock and the Web lock in the identity, checks installed versions and
rejects mismatch before creating journals or calling a server. CI installs its
test extras under the same runtime constraints. OS-specific wheels differ by
platform; exact package versions and semantic inputs are bound, not a claim
that native binaries are byte-identical across macOS/Linux.

```sh
PYTHONPATH=src:. python -m trading_desk.cli pipeline \
  --execution-mode candidate --request /absolute/input/request.json \
  --snapshot /absolute/input/dashboard-snapshot.json \
  --budget-journal /absolute/private/budget.sqlite \
  --state-dir /absolute/private/state --output /absolute/private/result.json \
  --dependency-lock web/package-lock.json \
  --dependency-lock config/pipeline-python-runtime.lock \
  --producer-build-sha EXACT_CHECKOUT_SHA
```

Recovery adds `--approved-recovery-plan` with an already approved exact plan.
Neither this command nor the workflow registers/approves it or claims its lease.
Resume adds `--resume-handoff-sha256`, attempt 2 and the original budget journal;
retain the previous owner's intent journal as evidence; a new state directory
creates a separately owner-bound journal. It cannot reset remote upload intents,
and completed publication recovery requires exact server verification.
Never initialize empty replacement journals to erase an ambiguous operation.

Environment credentials: FLOW_INGEST_API_KEY, FLOW_CF_ACCESS_CLIENT_ID and
FLOW_CF_ACCESS_CLIENT_SECRET. Do not place secrets in JSON, CLI arguments or logs.

The single manual workflow accepts fixture, dry-run or candidate. Candidate is
restricted to main and uses the exact SHA/lock. Source artifact ID/run ID identify
one existing collector artifact in xiaoker/flow. Bounded preparation validates
metadata, expiry, namespace, size, safe ZIP entries and exactly one snapshot;
only that snapshot is read, not a full extract. Tokens never follow the signed
archive redirect. Request and optional approved plan are validated non-secret
inputs. GHA candidate mode is **fresh only**; resumable journals are retained as
explicit evidence artifacts, and a separately scoped resume can use the local
command. No implicit retry, recollection or automatic resume is allowed.

Workflow dry-run with request_json uses that actual proposed request, not an
unrelated fixture. Empty request_json uses the explicitly local fixture. An
invalid declared identity/lock is rejected, and no source download, server grant
or candidate execution occurs. Approved recovery plan input is for candidate
mode only; dry-run checks declared scope, never actual approval authority.

An UNKNOWN CLI exit is nonzero. The workflow must not turn a STAGED candidate
with UNKNOWN total usage into successful completion. It saves the small result
and private bounded accounting/intent journals on failure. Source snapshots and
the whole state directory are not uploaded. Treat journal artifacts as private
operational evidence and preserve them for ambiguous-outcome reconciliation.

## Stopping and rollback

Stop on identity/hash/date/QA/lease/approval/budget errors. No active pointer is
changed, so there is no reader rollback. Do not delete orphan candidate objects,
clear UNKNOWN holds, replace journals or repeat dispatch to repair a failure.
Inspect exact recorded identities and receipts under a separately authorized
bounded operation. Hosted CI, merging, production invocation and canary are
separate actions; this document is not their authorization.
